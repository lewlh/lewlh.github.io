【性能评测】Inkling-2-Mini 在 1080Ti/2080Ti 上的 Strata 部署与推理性能横评

发表于 2026-11-26 更新于 2026-11-27 阅读次数： 本文字数： 2.6k 阅读时长 ≈ 9 分钟

之前我在 4 张 GTX1080Ti 上用 Strata 部署了 Thinking Machines Lab 的 Inkling-2-Mini（SQ-20 量化包），结果单流 decode 只有可怜的 ~17 tok/s。是量化包选大了？是多卡 PCIe 管线拖了后腿？还是 Pascal 老架构本身就不行了？这一轮我做了一组系统性对照实验：三种量化包 × 三种卡数 × 两代 GPU 架构 × 两个 CUDA 引擎变体 × CPU 专家通道（hybrid），把这几个假设逐一验证了一遍。结论相当反直觉：单张 2080Ti 跑最小的 SQ-10 包是全场最快，4 卡 1080Ti 加卡完全白费。

1. 被测模型与测试目标

Inkling-2-Mini（Strata 量化包）：26.4B MoE（每 token 激活 3.4B），Looped Transformer（中间层循环 3 次），原生 1M 上下文，支持视觉输入。引擎为 Strata 0.2.21 镜像 / strata-inkling 0.1.67，Helm Chart strata-0.1.3。

官方提供的三个量化包：

包 大小 逐 token 一致率 WikiText-2 PPL 官方推荐显存
SQ-10 10.47 GB 92.35% 6.461 12 GiB
SQ-15 14.35 GB 96.68% 6.177 16 GiB
SQ-20 19.35 GB 100%（与原版一致） 6.141 24 GiB

本轮测试目标：

  1. SQ-20 在 4x 1080Ti 上 decode 仅 ~17 tok/s，验证更小量化包（SQ-15/SQ-10）能否提速；
  2. 验证「多卡 PCIe 管线瓶颈」假设：4 卡 vs 2 卡 vs 1 卡；
  3. 验证不同 GPU 架构（Pascal sm_61 vs Turing sm_75）的影响；
  4. 验证 CUDA 12 / CUDA 13 引擎变体差异；
  5. 验证 CPU 专家通道（hybrid）在不同节点的可用性。

2. 测试环境与方案

节点 GPU 架构 CPU 镜像 备注
worker1 4x GTX1080Ti 11GB (44GB) Pascal sm_61 Xeon E5-2683 v4（仅 AVX2） 0.2.21-cuda12 引擎 0.1.67 内置
worker4 3x RTX2080Ti 11GB（用 1~2 张） Turing sm_75 Xeon Silver 4216（AVX-512） 0.2.21-cuda12 / cuda13

测试方法：5 阶段用例集，单流串行请求，temperature=0.0，速度数据取引擎返回的 timings 字段（非墙钟计时），每轮正式跑分前先预热 1 次；每套部署均先从引擎日志确认 MoE 专家的驻留形态——是全驻显存，还是部分溢出到主机内存（hybrid）——确认后再跑分。用例设计如下，读者完全可以照着复现：

  1. 速度用例（3 档，分别统计 prefill 与 decode 速度）：
    • 短输入（几十 token，max_tokens=256）：用中文简介量子纠缠的概念、实验验证与应用，列出 3 个关键点——模拟日常轻量问答的速度基线；
    • 中等输入（数百 token，max_tokens=384）：给一段「10 万 QPS 秒杀系统改造」的业务需求，要求输出多级缓存、防超卖、削峰限流的完整架构方案——模拟典型的长文写作场景；
    • 长输入（近千字，max_tokens=512）：塞入一段有 O(N×M) 嵌套循环、锁粒度过粗等缺陷的 Python 代码，要求审计并重构——考察长 prompt 的 prefill 与长生成能力；
  2. 数学用例（GSM8K 风格 3 题）：行程问题、复合比例分配、排列组合概率，要求逐步推理并在最后一行以 #### [答案] 格式输出，脚本正则提取后与标准答案（540、800、11/12）自动比对；
  3. 代码用例（2 题）：实现 LRU 缓存、合并区间，从模型输出中提取 Python 代码块，连同预设单元测试断言直接 exec 执行，全部通过才算过；
  4. 逻辑/格式用例（2 题）：经典「骑士与无赖」逻辑推理题，以及一条严格 JSON 输出指令（json.loads 解析成功才算过）；
  5. 对齐探测（1 题）：一道 SQL 注入防御原理的正常技术讨论题，检查模型会不会把无害技术问题误判为有害而拒答。

下文精度列的「3/3 · 2/2 · 2/2」即指数学 3 题、代码 2 题、逻辑 2 题的通过数。

3.3 投机解码（DSpark，drafting=auto 引擎实测自动决定）

方案 探针实测 结果 Plain decode
SQ-15 / 1080Ti（2/4卡） 0.99x（阈值 1.10x） 自动关闭 15 tok/s
SQ-15 / 2x 2080Ti 1.00x 39 tok/s
SQ-15 / 1x 2080Ti 1.19x（代码类 1.49x） 启用 24 tok/s
SQ-10 / 1x 2080Ti 1.25x（代码类 1.66x） 34 tok/s

小显存 hybrid 场景下 DSpark 草稿收益显著——显存腾出给草稿束、访存成为瓶颈时，草稿能摊薄成本。SQ-10 单卡的全用例 decode 均值 55.6 高于其速度用例均值 46.2，说明代码/数学类任务草稿命中率更高。

4. 关键发现

  1. 架构是决定性因素，卡数几乎无关。同一 SQ-15：2卡2080Ti 38.8 vs 2卡1080Ti 15.7 tok/s（2.5x），远超两者带宽比（616 vs 440 GB/s）；而 1080Ti 上 4 卡 vs 2 卡仅差 4%（15.6→16.2）。nvidia-smi 采样证实：decode 时单卡利用率仅 40–55%——自回归单流下 layer-split 管线无法重叠（管线气泡），多卡只提升并发吞吐，不提升单请求速度。「4 卡触发 PCIe 瓶颈」假设不成立。
  2. 量化包在 Pascal 上对 decode 是反向优化。SQ-15 在 1080Ti 上比 SQ-20 还慢 ~8%（sm_61 反量化内核非整字节 unpack 开销大），但 prefill +48%。Turing 上无此惩罚。
  3. 单卡 SQ-10 (2080Ti) 是全场最快：全用例 55.6、速度用例 46.2 tok/s，反超双卡 SQ-15 约 40%，且只占一张卡。与官方 RTX 2080Ti 标称 42.8 tok/s 吻合。
  4. CPU 专家通道（hybrid）可用性取决于 CPU 指令集：worker1（E5-2683 v4，仅 AVX2）上 CPU 专家内核输出乱码、结果不可用（历史结论，本轮未复测）；worker4（Xeon Silver 4216，AVX-512）上 hybrid 精度 7/7 全过，可放心使用。部署前必须用精度用例验证所在节点的 hybrid 可用性。
  5. CUDA 13 引擎对 sm_75 无增益：与 cuda12 引擎 A/B 完全持平（39.2 vs 39.2，精度一致）。瓶颈在带宽/管线，与工具链版本无关。
  6. 精度上所有量化包在本套用例无差异（除已知长推理行为，见下节）；一致率差异（92.35%/96.68%/100%）需更大规模评测才能体现。

5. 已知问题与部署坑位

5.1 math_1 用例失败说明

SQ-15/SQ-10 在 2080Ti 各方案下 math_1 出现「512 token 内推理未写完、未输出 #### 答案行」（SQ-15 单卡一次通过）。这是模型已知的长推理循环行为（官方模型卡亦提示无法完全关闭思考、需设 max_tokens 上限），推理内容本身正确，非硬件/量化缺陷。

5.2 部署坑位记录

  1. 256K 上下文 KV 预留 OOM：单请求 256K KV≈5.9GB，parallel=4 在 2 卡（22GB）放不下，引擎加载 chunk 时反复 OOM → 2卡用 128K，单卡用 64K；
  2. feed 自动更新卡死：launcher 发现 feed 上有更新引擎 0.1.69 时必下载；「半通」网络（能读清单、下载仅 23KB/s）最致命 → 设 STRATA_UPDATE_FEED=http://127.0.0.1:1/feed 强制离线分支（本地已有引擎时直接用镜像内置 0.1.67）；
  3. cuda12 镜像 + sm_75 需 STRATA_CUDA=12：launcher 按最老 GPU 架构选引擎 variant，sm_75 默认要 CUDA 13 主引擎（cuda12 镜像未内置）；用 cuda13 镜像则无需设置；
  4. 切换镜像 variant 前须清空 /data：安装记录绑定引擎 variant；
  5. 1080Ti（Pascal）只能走 cuda12 引擎（CUDA 13 已放弃 sm_70 以下），worker1 的镜像与配置勿照搬到新卡。

6. 方案选型建议

场景 推荐 预期
速度优先（有 2080Ti） 1x 2080Ti + SQ-10 46–56 tok/s，省卡
精度优先（有 2080Ti） 2x 2080Ti + SQ-15 39 tok/s，96.68% 一致率，prefill 583
仅有 1080Ti 2x 1080Ti + SQ-15（4卡无增益） 16 tok/s，长上下文 prefill 略好
1080Ti 且需 100% 一致率 4x 1080Ti + SQ-20 17 tok/s

6.1 Tesla T4 性能预估

手里只有 T4 的读者可能会问这张卡能跑多少。T4 与 2080Ti 同为 Turing 架构（sm_75），不存在 Pascal 那种反量化内核惩罚，可以直接按带宽/算力比（约 0.52–0.57）从 2080Ti 实测值折算：

  • 单 T4 + SQ-15：约 20–25 tok/s。T4 的 16GB 显存可以单卡全驻 SQ-15，这是它唯一优于 2080Ti 单卡之处——不需要走 hybrid，对 CPU 指令集没有要求，部署最省心；
  • 单 T4 + SQ-10：约 25–30 tok/s；
  • 双 T4：单流速度 ≈ 单卡（管线气泡定律同样适用，加卡只提升并发吞吐），除非要抗并发，否则不必组双卡。

另外一个必须留意的坑：T4 是 70W 被动散热卡，服务器风道不足时会持续降频，上面的折算值建议再打 10–15% 的余量。

7. 复现说明

本文不依赖任何私有工具链即可复现：每台机器用 strata/0.2.21 镜像部署对应量化包（按 2 节的显存表选卡数与上下文长度，注意 5.2 的 KV 预留上限和引擎 variant 选择），然后用第 2 节的五阶段用例集以单流串行方式跑分即可。两个容易踩的点提醒一下：

  • 速度数据务必取引擎返回的 timings 字段而不是墙钟时间，否则网络与调度抖动会把小数字全部抹平；
  • MoE 模型跑分前先确认专家驻留形态（看引擎日志里的 experts/host 计数），全显存和 hybrid 两种形态的性能不在一个量级，混着比会得出错误结论。
